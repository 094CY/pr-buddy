# 修改环节规范（Revision Protocol）

> **激活条件**：用户要求修改、迭代、润色、调整已有文章时加载本文件。
> **定位**：修改环节的唯一规则源（含历史版本保留）。修改完成后的验收仍走 `final-check.md`。

---

## 一、修改前：先诊断，再动手

**收到修改指令后，不要立即动手改。按以下步骤诊断：**

### 1.0 历史版本保留检查

动手修改前，先用 `stat` 检查目标文件的最后修改时间（mtime）：
- 如果 mtime 距当前 **≥ 3 天**：**覆盖前必须先将旧文件重命名保留**，命名格式 `原文件名_V旧版本号_YYYYMMDD.ext`（如 `春季上新-种草笔记_V1_20260405.md`），新文件使用原文件名
- 如果 mtime < 3 天（同一工作会话或近期连续迭代）：直接修改，不触发保留
- 适用于项目文件夹中的所有交付物格式（.md / .html / .docx）

❌ **禁止**：不检查 mtime 就直接覆盖——跨会话大改后丢失前版本是不可逆损失

### 1.0.5 先判断意见针对哪一层

用户或客户的意见可能针对：核心信息（主张不成立、受众不买账）、结构（顺序、比重）、表述（措辞、语气、品牌调性）、事实（产品信息、数据、客户信息）。先判断层级，再决定动作：

- **否定核心信息**：回到 SKILL.md Step 4.5 重做写前论证卡，判定通过后重写；不在原稿上换词修补。
- **否定结构或表述**：只改被否定的那一层；否定某种表述时，换一种说法把它承载的信息留住，不连同信息一起删。
- **事实问题**：回 Step 1.6 核实后修正，检查所有引用该事实的位置。
- 一条意见涉及多层时，从最深的一层开始处理。

### 1.1 通读全文

完整通读当前版本，理解：
- 全文结构和论证主线
- 各章节的角色分工
- 当前字数和各章比例
- 上一轮修改的内容和原因

❌ **禁止**：不读全文就改局部——局部最优≠全局最优

### 1.2 定位问题清单

列出本轮需要修改的具体问题：
- 哪些段落/句子有问题
- 什么类型的问题（措辞/结构/字数/逻辑/事实/合规/安全性...）
- 影响范围（仅局部 / 波及上下游 / 全文性问题）

### 1.3 评估影响链

判断修改 A 是否会影响 B、C、D：
- 删除/新增内容对前后文衔接的影响
- 对全文论证链的影响（改了第三章的结论，结语是否还成立？）
- 对字数平衡的影响
- 对引用来源的影响

## 二、修改中：执行纪律

### 2.1 幅度匹配

**修订幅度必须匹配指令幅度：**

| 用户指令 | 正确操作 | 错误操作 |
|----------|----------|----------|
| "这段话术不好" | 改那段话术 | 顺手重构整章 |
| "微调一下措辞" | 只调措辞 | 推倒重来重写 |
| "这章结构有问题" | 重组该章结构 | 只改了几个词 |
| "整体重写" | 整体重写 | 修修补补 |

### 2.2 输出规则

- **局部修改**：在文件里就地修改对应段落，回复里只说明改了哪里，不在对话里重贴全文；用户明确要“完整版”时再输出全文
- **结构性修改**（涉及章节增删/重组）：整体重写文件，回复里给出新结构
- 无论哪种，修改完成后必须全文通读验证连贯性

### 2.3 删了就是删了，不回塞

**铁律**：
- 一旦判断某段内容是冗余并删除，后续**不得**为凑字数或补空缺把同样的内容换说法塞回去
- 如果删除后论证断裂，用**新的论据/新的角度**补充，不回收旧内容
- 如果确实需要恢复之前删除的内容，必须明确说明恢复理由

### 2.4 新增内容必须预评估

新增一个段落/章节之前，先回答三个问题：
1. 它在全文论证链中扮演什么角色？
2. 预估多少字？对全文字数和各章比例的影响？
3. 新增后是否有其他段落因此变得冗余、需要同步压缩？

### 2.5 不制造新问题

每次修改后自检：
- 是否引入了新的 AI 痕迹？（对照 `references/anti-ai-traces.md`）
- 是否引入了新的逻辑矛盾？（对照 `final-check.md` 维度 3）
- 是否破坏了原有的节奏感？是否把自然的原文改成“首先/其次/最后”式机械结构？
- 修订后的文字风格是否与原文其余部分一致？
- 是否把前文已展开的数据、论点在别处又复述了一遍？
- 是否引入了贬低同行、激进表述或新的合规用语？（对照 `final-check.md` 维度 4、维度 8 和 `compliance-notes.md`）

### 2.6 同类问题全文扫描

**铁律**：
- 用户指出某处**措辞偏颇/不中立/贬义/煽情/事实错误/合规用语**，不能只改被点名的那一处
- 必须全文扫描同类问题，一轮清完
- 同理适用于：错别字、标点不统一、同一个 AI 痕迹信号反复出现、格式不一致等

## 三、修改后：验收流程

### 3.1 全文通读

修改完成后必须完整通读修改后的全文，检查：

| 检查项 | 具体操作 |
|--------|----------|
| 前后文衔接 | 修改处的上一段和下一段读起来是否顺畅 |
| 论证链完整性 | 全文的论证线索是否还成立 |
| 各章比例 | 有没有某章突然膨胀/萎缩 |
| 遗漏连带修改 | 改了正文某处，字数标注、信息缺口清单等是否需要同步 |
| 重复论点 | 多轮修改后，有没有不同位置说了同样的观点 |

发现问题当场修，不交给用户当质检员。

### 3.2 文本质量扫描

每轮修改后，对修改涉及的段落重新执行以下检查：

| 检查项 | 标准 |
|--------|------|
| **错别字/同音字** | 逐字检查修改段落，特别注意常见混淆：的/地/得、已/以、在/再、做/作 |
| **标点符号** | 中文语境用中文标点，英文/代码/专有名词内保留英文标点，全文统一 |
| **AI 痕迹信号** | 对照 `references/anti-ai-traces.md` 看修改段落有没有新增堆砌的信号词和套路句式（看语境，不一刀切） |
| **数字/人名/公司名** | 修改涉及的事实性内容是否准确 |
| **主体信息一致性** | 名称、规格、价格、资质、能力描述是否与事实表（`references/brand-fact-sheet.md`）及一手资料一致 |
| **合规用语** | 修改段落有没有新增绝对化、功效、承诺、价格类表述（对照 `references/compliance-notes.md`，看语境和证据） |
| **格式一致性** | 加粗、引用块、列表等 Markdown 格式是否与全文统一 |

### 3.3 机械检查与字数

- 重跑 `python3 <本 Skill 目录>/references/article_lint.py <文章.md>`，ERROR 清零，REVIEW 按语境逐条判断
- 头部字数以 `wordcount.py` 结果更新

### 3.4 差异说明

简要说明本轮改了什么、为什么改、改后字数。几句话说清楚，不写长篇报告。

## 四、字数管理原则

> **核心理念：字数是参考线，不是填充指标。内容完整性和节奏感优先于字数。**

- 用户给的字数目标是参考范围——**±10% 都合理**
- **字数目标不是 KPI，不是必须精确命中的数字**
- 达不到目标时：告诉用户"当前内容已经完整，继续添加会导致臃肿"
- 超出目标时：检查冗余但不砍有价值论证
- **扩充**是因为分析不够深，**压缩**是因为有废话——两个方向都基于内容质量判断

## 五、结构调整规范

### 5.1 先画结构图再动手

用一句话描述每章的角色，确保调整后每章仍有明确且不重复的角色。

### 5.2 承载力评估

- 当前字数目标能否容纳新章节？
- **框架融合前评估最小字数需求**——不够就跟用户商量扩容或拆分

### 5.3 删除章节的引用链检查

- 其他章节有没有引用被删章节的论点？
- 字数标注、信息缺口清单是否需要同步更新？

## 六、观点安全与措辞修改专项

### 6.1 触发条件

用户指出任何一处措辞问题（偏颇/贬义/煽情/不中立/不准确），立即触发全文扫描。

### 6.2 扫描清单

| 扫描维度 | 典型问题 | 正确处理 |
|----------|----------|----------|
| **立场偏颇** | 标题、副标题带有倾向性 | 改为中性描述 |
| **贬低同行** | 暗示同行不行的句式 | 改为讲自身事实 |
| **过激表述** | 绝对化判断 | 加限定或改客观描述 |
| **合规用语** | 绝对化、功效、承诺、价格类表述 | 按 `references/compliance-notes.md` 改写或补依据 |
| **品牌调性** | 措辞与主体调性不符 | 回到 Step 1.5 判定的品牌调性 |

### 6.3 一轮清完原则

- 全文扫描、列出所有同类问题、一轮全部修完
- 不要这轮改三处、下一轮用户又指出另外五处

## 七、与 SKILL.md 其他规则的协同

修改环节不是独立运行的——它与 SKILL.md 的以下规则联动：

| 修改场景 | 联动规则 | 操作 |
|----------|----------|------|
| 修改前版本保留 | 本文件 1.0 | 文件 mtime ≥ 3 天时，覆盖前先重命名旧文件保留 |
| 修改后交付 | `final-check.md`（脚本 + 判断维度） | 修改涉及的维度必须重新过检 |
| 修改涉及措辞 | 去AI痕迹规则 | 对修改段落重看 AI 痕迹信号的语境与密度 |
| 修改涉及事实 | 事实强制刹车 | 新增/修改的事实性内容必须查证 |
| 修改涉及主体信息 | 主体画像 Step 1.5 + 事实校准 Step 1.6 | 与事实表和一手资料核对 |
| 修改涉及功效/价格/承诺 | 合规边界（论证卡第 8 项） | 重看合规边界是否还成立，必要时更新论证卡 |
| 修改后定稿 | 交付节奏（铁律 2） | 初稿阶段只出 .md；定稿确认后才出 docx/HTML |

## 八、高频问题速查表

| # | 问题类型 | 典型症状 | 正确处理 |
|---|----------|----------|----------|
| 1 | **字数死板拼凑** | 为凑目标字数把已删内容换说法塞回 | 告知用户当前字数已够，硬凑只会臃肿 |
| 2 | **局部改完不看全局** | 改了某章但结语还在引用旧版论点 | 改完必须全文通读，检查上下游 |
| 3 | **措辞只改一处** | 用户指出一处，同类问题其他段落还在 | 全文扫描同类问题，一轮清完 |
| 4 | **新增内容不预估** | 随手扩写导致某章严重臃肿 | 新增前先预估字数，考虑全文比例 |
| 5 | **修改引入新AI痕迹** | 把自然原文改成机械结构 | 对照 anti-ai-traces.md 重检修改段落 |
| 6 | **主体信息不同步** | 改了产品或服务描述但没核对一手资料 | 修改相关内容时必须重做事实校准 |

*宣发内容修改的重点：主体信息一致性、合规与观点安全、品牌调性。*
